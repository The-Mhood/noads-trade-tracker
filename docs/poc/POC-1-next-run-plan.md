## 1. What counts as supported

MetaApi's [trade model](https://metaapi.cloud/docs/client/models/metatraderTrade/) lists `ORDER_TYPE_BUY`, `SELL`, `BUY_LIMIT`, `SELL_LIMIT`, `BUY_STOP`, `SELL_STOP`, `BUY_STOP_LIMIT`, `SELL_STOP_LIMIT` plus `ORDER_MODIFY`, `ORDER_CANCEL`, `POSITION_MODIFY`, `POSITION_CLOSE_ID`. Its [symbol specification](https://metaapi.cloud/docs/client/models/metatraderSymbolSpecification/) exposes `allowedOrderTypes` (MARKET, LIMIT, STOP, STOP_LIMIT), `tradeMode`, filling/expiration modes, trade sessions, min/step/max volume, stops/freeze levels and currency/margin facts. **Published API support ≠ this demo server's actual support.** At preflight, capture the target broker's current specification. Test every type the configuration permits; if a type is disallowed, record `UNSUPPORTED` with spec plus definitive broker evidence where safely available, never fake a success or force an invalid order. A live rejection of a spec-advertised type is **FAIL/contradiction**, not `UNSUPPORTED` by assumption. If the broker offers an additional entry type explicitly adopted into project scope, add it to the numbered matrix and tests *before* sending it.

Stop-limit uses `openPrice` (stop trigger) and `stopLimitPrice` (limit price; documented as a string in the command model) and requires a separate broker-side readback of **both** prices. Do not guess which broker/MetaApi fields survive conversion to a resulting position. Current endpoint/type details and the comment/clientId length conflict are recorded in [provider evidence](MetaApi-provider-evidence.md). No comment or clientId is broker-enforced idempotency.

## 2. Numbered entry-case matrix (one target account/symbol)

Choose the smallest valid broker lot (never round up beyond the risk ceiling); only validated current symbol, conversion, session, margin, quote and stop/freeze constraints permit a send. **Exactly one first submission per supported row; no retry of an ambiguous request.** Each row needs authenticated exact-account identity, durable pre-send intent, MetaApi transport + numericCode, broker-linked ticket/deal/position/history, actual volume/price, broker-stored SL and TP, reconciled cleanup, and an auditable verdict. A market fill is **not** an accepted pending order; a pending order acceptance is **not** a fill. Directional quote for BUY uses ask and SELL uses bid. A natural broker rejection is evidence of that case's **FAIL** (or `UNSUPPORTED` only with corroborated spec); a deliberately bad-symbol order is not needed for every row.

| ID | Entry action / preflight entitlement | Mandatory accepted-state evidence and cleanup | PASS / FAIL / UNKNOWN / UNSUPPORTED |
|---|---|---|---|
| E01 | `ORDER_TYPE_BUY`, spec MARKET + long allowed | Min lot with SL below and TP above the actual filled entry; linked order/deal/position; **position** stored SL/TP confirmed; planned `POSITION_CLOSE_ID` only for identified expected position, then linked close/deal/position final state. | PASS only if confirmed protection, actual risk/fill and authoritative zero remaining exposure; reject/mismatch = FAIL, uncertain fill/close = UNKNOWN. |
| E02 | `ORDER_TYPE_SELL`, MARKET + short allowed | Mirror E01: SELL uses bid, SL above/TP below filled entry; confirm position SL/TP; one planned close and final reconciliation. | Same four-way criteria; short-side math and conversion independently verified. |
| E03 | `ORDER_TYPE_BUY_LIMIT`, LIMIT + long allowed | One away-from-market pending order; read back exact ticket, entry, min volume/residual, broker-stored SL/TP, optionally same-ticket MT5 Trade-tab capture; one planned cancel **only while unequivocally unfilled**, then final order/deal/position/history. | PASS only on confirmed pending protection, final canceled+zero fill/exposure; any fill/partial invokes incident path, not clean PASS. |
| E04 | `ORDER_TYPE_SELL_LIMIT`, LIMIT + short allowed | Mirror E03 with entry above market, SL above/TP below; independent broker readback, safe cancel and finality. | Same criteria, not inferred from E03 or manual MT5 orders. |
| E05 | `ORDER_TYPE_BUY_STOP`, STOP + long allowed | Trigger above market; pending SL/TP readback; planned single cancel while unfilled; deal/position/history reconciliation. | Same criteria; an observed fill requires position SL/TP and incident handling. |
| E06 | `ORDER_TYPE_SELL_STOP`, STOP + short allowed | Trigger below market; pending SL/TP readback; planned single cancel while unfilled; finality. | Same criteria, no inference from E05. |
| E07 | `ORDER_TYPE_BUY_STOP_LIMIT`, STOP_LIMIT + long allowed | Validate trigger and limit price relationships from broker specification; read back **both** broker-stored `openPrice`/`stopLimitPrice`, volume, SL/TP; cancel only known-unfilled ticket, reconcile residual/history. | PASS on complete readback and final zero exposure; mark UNSUPPORTED only with broker-spec evidence; if transition/fill races, UNKNOWN/incident. |
| E08 | `ORDER_TYPE_SELL_STOP_LIMIT`, STOP_LIMIT + short allowed | Mirror E07 with independent trigger, limit and SL/TP checks. | Same four-way criteria; API type documentation alone does not prove broker acceptance. |

**Count:** up to **eight first placements** (two market, six pending), **up to six** planned pending cancellations (one per unfilled ticket), **up to two** planned closes (one per identified market position); at most one planned pending modification per *supported* pending subtype **if** M01 below can be safely validated. Unsupported rows consume **zero** placement intents. Any ambiguous POST consumes its case allowance and halts conflicting sends; do not silently replace it with another attempt. Do **not** force fills/partial fills by larger lots or near-market pending prices. Exact case prices, lot/risk budget, quote age/skew and backoff numbers are chosen from current broker specification and signed into the local run manifest before sends; invalid/unknown inputs → no trade, not a fabricated default.

Cancel acknowledgement or disappearing pending order alone is not finality. | Ambiguous cancel/close = UNKNOWN; **never blind retry**. | L04 reconciliation and duplicate prevention | Read linked orders/deals/positions/history by ticket/position, paginate complete time windows, account for source timestamps and synchronization/gaps; reconcile original and any accepted revision. Late evidence re-blocks. Offline PASS is not provider proof. |

**Modification and partial-fill scope:** The six pending-order modification checks are conditional on broker capability and independently validated safe revision prices. They do not increase size or move SL farther from entry; failure/unsupported is recorded separately from entry-type success. Broker-side position modification, forced partial fills and induced network outages are **not** part of automatic base execution; offline failure simulations cover safety behavior. If these empirical operations are deemed mandatory for the Phase 1 design, POC-1 remains OPEN until independently validated or explicitly accepted as limitations with fail-closed product controls. Planned closes of *expected* market test positions are part of this authorization; unexpected exposure is not.

## 4. Safe sequence and cleanup ownership

1. Check exact intended account and current symbol specification/quotes, linked orders, positions and known test journals; reject any unresolved earlier intent. Smallest valid lot only; all entry/SL/TP/stop-limit/modify prices rounded to broker tick/digits and revalidated after rounding. Protect against quote age, clock skew, session/stop/freeze and currency/margin unknowns. No test while disconnected/undeployed or without usable balance.
2. Run **one case at a time**, no fan-out. Write/fsync durable pre-submit intent with a single-use case key. A crash, network exception, timeout or process restart must enter **read-only** recovery, not automatically send. Record exact account, response and broker ticket without writing secrets to Git/logs. Do not adopt a sole account on server-name match.
3. After acknowledged placement, read the *current broker object* and all linked exposure; verify type, accepted price(s), volume, protection. A market order must have a matching position with broker-held SL/TP. If any mismatch/partial/uncertainty, stop subsequent placements, fence appropriately, alert and hand off; **do not blindly close unexpected exposure**. If a pending order remains unfilled and modification is safe, validate/record that separate revision before proceeding.
4. Cancel only a known-unfilled pending original ticket; close only its own expected, fully identified market test position. Persist cleanup intent before POST. Reconcile final order/position and linked deal history, accounting for delayed/partial fills and complete pagination/synchronization. No cancel retry based on HTTP status alone. Provider history's negative finality remains broker-dependent: if zero-fill cannot be shown with sufficiently complete synchronized evidence and owner terminal corroboration if needed, label UNKNOWN and stop.
5. Before next case, require account-level no-conflict proof and a clean test baseline. After all cases, explicitly record remaining positions/orders, resource state and any still-accruing provider charge; owner controls funding. If test cannot be safely completed, stop provider-dependent operations only, continue offline, and give a precise incident ticket/status. A local timer or request limit never implies zero exposure. Do not delete/undeploy an unrelated or shared resource.
